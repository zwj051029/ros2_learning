# ROS 2 动作通信总结

## 一句话理解

动作通信用于**执行时间较长、需要持续反馈、允许取消的任务**。

动作客户端发送目标后，动作服务端会经历：

```text
接收或拒绝目标
       ↓
执行任务并持续反馈
       ↓
成功、取消或中止
       ↓
返回最终结果
```

典型应用包括机器人导航、机械臂运动、定角度旋转和长时间计算。

## Goal、Result 和 Feedback

动作接口使用 `.action` 文件，通过两个 `---` 分成三部分：

```text
# Goal
int32 num
---
# Result
int64 sum
---
# Feedback
float32 progress
```

| 部分 | 作用 | 发送方向 |
| --- | --- | --- |
| Goal | 描述客户端希望完成的任务 | 客户端到服务端 |
| Result | 描述任务最终结果 | 服务端到客户端 |
| Feedback | 描述执行过程中的状态 | 服务端持续发送给客户端 |

动作在底层组合使用了多个服务和话题，但日常开发应通过 `rclcpp_action` 或 `rclpy.action` 提供的高级 API 使用它。

## 动作与话题、服务的区别

| 特性 | 话题 | 服务 | 动作 |
| --- | --- | --- | --- |
| 持续数据 | 适合 | 不适合 | 反馈可以持续发送 |
| 明确最终结果 | 没有 | 有 | 有 |
| 执行进度 | 需要自行设计 | 没有 | 原生支持 Feedback |
| 取消任务 | 没有 | 没有 | 原生支持 |
| 典型耗时 | 任意数据流 | 较短 | 较长 |

判断方法：

- 连续广播数据：话题。
- 请求一次、快速返回：服务。
- 任务耗时较长，需要进度或取消：动作。

## 动作状态

常见最终状态：

| 状态 | 含义 |
| --- | --- |
| `SUCCEEDED` | 任务正常完成 |
| `CANCELED` | 客户端请求取消，服务端接受并完成取消 |
| `ABORTED` | 服务端主动中止任务 |

目标被拒绝发生在任务开始前，此时不会进入执行阶段，也不会得到普通的成功结果。

动作状态与业务字段要分开理解：

- ROS 动作状态表示任务如何结束。
- Result 中的 `success`、`message` 等字段表示业务结果。

二者应该保持一致，避免状态显示成功但业务字段却表示失败。

## C++ 动作服务端结构

需要包含：

```cpp
#include "rclcpp/rclcpp.hpp"
#include "rclcpp_action/rclcpp_action.hpp"
```

创建动作服务端时需要提供三个回调：

```cpp
server_ = rclcpp_action::create_server<ActionType>(
    this,
    "action_name",
    std::bind(&ActionServer::goal_callback, this, _1, _2),
    std::bind(&ActionServer::cancel_callback, this, _1),
    std::bind(&ActionServer::accepted_callback, this, _1)
);
```

### 目标处理回调

```cpp
rclcpp_action::GoalResponse goal_callback(
    const rclcpp_action::GoalUUID &uuid,
    std::shared_ptr<const ActionType::Goal> goal
) {
    (void)uuid;

    if (!goal_is_valid(goal)) {
        return rclcpp_action::GoalResponse::REJECT;
    }

    return rclcpp_action::GoalResponse::ACCEPT_AND_EXECUTE;
}
```

目标处理回调只负责：

- 检查请求是否合法。
- 接受或拒绝目标。

不应在这里直接执行耗时任务。

### 取消处理回调

```cpp
rclcpp_action::CancelResponse cancel_callback(
    const std::shared_ptr<GoalHandle> goal_handle
) {
    (void)goal_handle;
    return rclcpp_action::CancelResponse::ACCEPT;
}
```

返回 `ACCEPT` 只表示愿意取消。执行循环还需要检查 `is_canceling()`，并调用 `canceled()`，取消才真正完成。

### 目标接受回调

```cpp
void accepted_callback(
    const std::shared_ptr<GoalHandle> goal_handle
) {
    std::thread(
        std::bind(&ActionServer::execute, this, goal_handle)
    ).detach();
}
```

耗时任务通常放到独立线程，避免阻塞执行器，使服务端仍能处理取消请求和其他回调。

简单地为每个目标创建线程不代表已经安全支持并发目标。多个目标如果共享机器人位置或其他成员变量，还需要拒绝并发目标或使用互斥锁保护共享状态。

## C++ 执行循环

```cpp
void execute(const std::shared_ptr<GoalHandle> goal_handle) {
    auto feedback = std::make_shared<ActionType::Feedback>();
    auto result = std::make_shared<ActionType::Result>();
    rclcpp::Rate rate(2.0);

    while (!task_finished) {
        rate.sleep();

        if (goal_handle->is_canceling()) {
            fill_canceled_result(result);
            goal_handle->canceled(result);
            return;
        }

        update_task_state();
        fill_feedback(feedback);
        goal_handle->publish_feedback(feedback);
    }

    fill_success_result(result);
    goal_handle->succeed(result);
}
```

推荐顺序：

1. 等待一个执行周期。
2. 在改变任务状态前检查取消。
3. 更新状态。
4. 计算并发布反馈。
5. 任务完成后填写结果并调用 `succeed()`。

取消检查放在状态更新之后，可能导致客户端已经请求取消，机器人却又多执行一步。

## 进度和最后一步

常见进度公式：

```text
progress = completed / total
```

应限制到 `[0.0, 1.0]`：

```cpp
progress = std::min(completed / total, 1.0);
```

浮点数在内存中通常无法精确表示十进制小数，因此可能看到：

```text
0.699999988
0.899999976
```

这是正常现象。打印百分比时可以使用四舍五入：

```cpp
static_cast<int>(std::round(feedback->progress * 100))
```

涉及机器人位置、角度和路程时，最后一步应该使用：

```text
actual_step = min(normal_step, remaining_distance)
```

避免超过目标位置。

## C++ 动作客户端

客户端通常设置三个回调：

```cpp
auto options =
    rclcpp_action::Client<ActionType>::SendGoalOptions();

options.goal_response_callback =
    std::bind(&ActionClient::goal_response_callback, this, _1);
options.feedback_callback =
    std::bind(&ActionClient::feedback_callback, this, _1, _2);
options.result_callback =
    std::bind(&ActionClient::result_callback, this, _1);

client_->async_send_goal(goal, options);
```

| 回调 | 作用 |
| --- | --- |
| Goal Response | 判断目标被接受还是拒绝 |
| Feedback | 接收任务进度和中间状态 |
| Result | 根据最终状态处理结果并退出 |

目标句柄为 `nullptr` 时表示目标被拒绝。

取消目标：

```cpp
client_->async_cancel_goal(
    goal_handle,
    cancel_response_callback
);
```

取消请求被接受后，客户端仍应等待最终 `CANCELED` 结果，不能一发送取消请求就直接关闭节点。

## Python 动作服务端

```python
from rclpy.action import ActionServer
from rclpy.action import CancelResponse, GoalResponse


class ExampleActionServer(Node):
    def __init__(self):
        super().__init__("example_action_server_py")
        self.server_ = ActionServer(
            self,
            ActionType,
            "action_name",
            execute_callback=self.execute_callback,
            goal_callback=self.goal_callback,
            cancel_callback=self.cancel_callback
        )

    def goal_callback(self, goal_request):
        if not self.goal_is_valid(goal_request):
            return GoalResponse.REJECT
        return GoalResponse.ACCEPT

    def cancel_callback(self, goal_handle):
        return CancelResponse.ACCEPT
```

执行回调：

```python
def execute_callback(self, goal_handle):
    feedback = ActionType.Feedback()
    result = ActionType.Result()

    while not task_finished:
        if goal_handle.is_cancel_requested:
            fill_canceled_result(result)
            goal_handle.canceled()
            return result

        update_task_state()
        fill_feedback(feedback)
        goal_handle.publish_feedback(feedback)

    fill_success_result(result)
    goal_handle.succeed()
    return result
```

Python 服务端必须返回 Result 对象：

```python
goal_handle.succeed()
result = ActionType.Result()
return result
```

`succeed()` 负责修改动作状态，`return result` 负责把结果数据返回给客户端，二者缺一不可。

## Python 回调组和多线程执行器

耗时执行回调如果阻塞单线程执行器，取消回调可能无法及时运行。

可以使用：

```python
from rclpy.callback_groups import ReentrantCallbackGroup
from rclpy.executors import MultiThreadedExecutor

self.callback_group_ = ReentrantCallbackGroup()

self.server_ = ActionServer(
    self,
    ActionType,
    "action_name",
    callback_group=self.callback_group_,
    execute_callback=self.execute_callback,
    goal_callback=self.goal_callback,
    cancel_callback=self.cancel_callback
)
```

```python
executor = MultiThreadedExecutor()
executor.add_node(server)
executor.spin()
```

`MultiThreadedExecutor` 不会简单地按照“一个回调固定对应一个线程”工作。它维护线程池，并让满足回调组约束的就绪回调获得执行机会。

`ReentrantCallbackGroup` 允许同一回调组中的多个回调并行执行，因此还要考虑共享数据的线程安全。

## Python 动作客户端

发送目标：

```python
goal = ActionType.Goal()
goal.target = target

future = self.client_.send_goal_async(
    goal,
    feedback_callback=self.feedback_callback
)
future.add_done_callback(self.goal_response_callback)
```

处理目标响应：

```python
def goal_response_callback(self, future):
    goal_handle = future.result()

    if not goal_handle.accepted:
        self.get_logger().error("目标被拒绝")
        return

    result_future = goal_handle.get_result_async()
    result_future.add_done_callback(self.result_response_callback)
```

`get_result_async()` 返回的 Future 完成后，`future.result()` 得到的是包装结果，通常包含：

```text
wrapped_result.status
wrapped_result.result
```

`status` 是动作状态，`result` 才是 `.action` 中定义的 Result 数据。

```bash

```

```text
功能包/action/接口名
```

## 常见问题

### 取消请求被接受，但任务继续执行

检查：

- 服务端执行循环是否调用 `is_canceling()` 或 `is_cancel_requested`。
- 取消后是否调用 `canceled()`。
- 取消分支是否立即 `return`。
- 执行器是否被耗时回调阻塞。
- 客户端是否只停止显示反馈，却没有真正发送取消请求。

### 服务端多执行了一步

取消检查位置太晚。应在更新机器人状态前检查取消。

### 目标被拒绝后客户端仍返回成功退出码

客户端需要记录目标是否被拒绝，并让主程序返回非零退出码。日志中的“拒绝”与进程退出状态是两件事。

### 服务端消失后客户端一直等待

动作 Future 不一定会因为对端进程突然退出而立即完成。工程中可以增加超时定时器、服务端状态监测或生命周期管理。学习阶段至少要知道这种情况存在。

### 并发目标导致状态混乱

多个执行线程同时修改当前位置等成员变量会发生数据竞争。可以：

- 服务端忙碌时拒绝新目标。
- 使用互斥锁保护共享状态。
- 将每个目标的数据与共享状态明确分离。

## 复习清单

- 能解释 Goal、Result 和 Feedback。
- 能区分接受目标、执行任务和返回结果三个阶段。
- 能实现目标校验、取消处理和耗时执行。
- 能正确调用 `succeed()`、`canceled()` 或 `abort()`。
- 能在客户端处理目标响应、反馈、取消响应和最终结果。
- 能解释为什么耗时任务需要独立线程或多线程执行器。
- 能正确计算进度，并处理浮点显示误差。
- 能避免取消后多执行一步和最后一步越过目标。
- 能使用 `ros2 action send_goal --feedback` 独立测试服务端。
