# ROS 2 服务通信总结

## 一句话理解

服务通信是一种**请求与响应模型**：

1. 客户端发送一次请求。
2. 服务端处理请求。
3. 服务端返回一次响应。
4. 客户端根据 Future 获取结果。

它适合执行时间较短、需要明确答复的操作，例如查询地图信息、切换机器人模式、管理航点和触发设备操作。

## 核心组成

| 组成 | 作用 |
| --- | --- |
| Service Server | 接收请求、处理业务并填写响应 |
| Service Client | 等待服务、发送请求并获取响应 |
| Service Name | 服务名称，例如 `/sum` |
| Service Type | 请求和响应的数据结构 |
| Future | 表示尚未完成的异步响应 |

服务与话题的主要区别：

| 对比 | 话题 | 服务 |
| --- | --- | --- |
| 数据方向 | 发布方到订阅方 | 客户端请求，服务端响应 |
| 是否等待结果 | 否 | 是 |
| 通信频率 | 通常持续发送 | 通常按需调用 |
| 典型用途 | 传感器、状态、控制流 | 查询、配置、短任务 |

服务不适合持续反馈和长时间运行任务。此类需求应使用动作通信。

## 自定义服务接口

服务接口使用 `.srv` 文件，请求和响应通过 `---` 分隔：

```text
# AddInts.srv
int32 num1
int32 num2
---
int32 sum
```

上半部分是 Request，下半部分是 Response。

生成接口：

```cmake
find_package(rosidl_default_generators REQUIRED)

rosidl_generate_interfaces(${PROJECT_NAME}
  "srv/AddInts.srv"
)
```

构建并查看接口：

```bash
colcon build --packages-select base_interfaces
source install/setup.bash
ros2 interface show base_interfaces/srv/AddInts
```

## C++ 服务端

典型流程：

1. 继承 `rclcpp::Node`。
2. 使用 `create_service()` 创建服务。
3. 在回调中读取请求。
4. 填写响应。
5. 使用 `rclcpp::spin()` 等待请求。

```cpp
#include "base_interfaces/srv/add_ints.hpp"
#include "rclcpp/rclcpp.hpp"

using AddInts = base_interfaces::srv::AddInts;
using std::placeholders::_1;
using std::placeholders::_2;

class SumServer : public rclcpp::Node {
public:
    SumServer() : Node("sum_server_cpp") {
        server_ = this->create_service<AddInts>(
            "sum",
            std::bind(&SumServer::sum_callback, this, _1, _2)
        );
    }

private:
    void sum_callback(
        const AddInts::Request::SharedPtr request,
        const AddInts::Response::SharedPtr response
    ) {
        response->sum = request->num1 + request->num2;
    }

    rclcpp::Service<AddInts>::SharedPtr server_;
};
```

服务对象要保存为成员变量。响应对象由 ROS 2 创建，回调只需要填写字段，不需要手动返回指针。

## C++ 客户端

典型流程：

1. 使用 `create_client()` 创建客户端。
2. 使用 `wait_for_service()` 等待服务端。
3. 创建 Request 并填写字段。
4. 使用 `async_send_request()` 发送请求。
5. 使用 `spin_until_future_complete()` 等待响应。
6. 从 Future 中取出结果。

```cpp
auto client = node->create_client<AddInts>("sum");

while (!client->wait_for_service(1s)) {
    if (!rclcpp::ok()) {
        return 1;
    }
    RCLCPP_INFO(node->get_logger(), "服务端连接中...");
}

auto request = std::make_shared<AddInts::Request>();
request->num1 = 10;
request->num2 = 20;

auto future = client->async_send_request(request);

if (
    rclcpp::spin_until_future_complete(node, future) ==
    rclcpp::FutureReturnCode::SUCCESS
) {
    auto response = future.get();
    RCLCPP_INFO(node->get_logger(), "sum = %d", response->sum);
}
```

`async_send_request()` 不会立刻得到响应，而是返回 Future。只有 Future 完成后才能安全读取响应。

如果自定义的 `send_request()` 声明了非 `void` 返回类型，就必须返回 `async_send_request()` 的结果，否则会产生未定义行为，严重时可能段错误。

## Python 服务端

```python
import rclpy
from rclpy.node import Node

from base_interfaces.srv import AddInts


class SumServer(Node):
    def __init__(self):
        super().__init__("sum_server_py")
        self.server_ = self.create_service(
            AddInts,
            "sum",
            self.sum_callback
        )

    def sum_callback(self, request, response):
        response.sum = request.num1 + request.num2
        return response
```

Python 服务回调必须返回 `response`。如果忘记返回，客户端可能得到异常或空结果。

## Python 客户端

```python
class SumClient(Node):
    def __init__(self):
        super().__init__("sum_client_py")
        self.client_ = self.create_client(AddInts, "sum")

    def send_request(self, num1: int, num2: int):
        request = AddInts.Request()
        request.num1 = num1
        request.num2 = num2
        return self.client_.call_async(request)
```

等待响应：

```python
future = client.send_request(10, 20)
rclpy.spin_until_future_complete(client, future)

try:
    response = future.result()
except Exception as exception:
    client.get_logger().error(f"服务请求失败: {exception}")
else:
    client.get_logger().info(f"sum = {response.sum}")
```

`try` 用来捕获请求处理、通信或 Future 中保存的异常；`else` 只在没有异常时执行。

## 服务业务结果设计

通信成功不等于业务成功。例如“删除不存在的航点”时，服务请求和响应正常完成，但业务应该失败。

推荐在响应中加入：

```text
bool success
string message
```

服务端处理原则：

1. 先验证请求。
2. 请求非法时设置 `success = false` 和失败原因。
3. 请求非法时不修改原有状态。
4. 请求合法时更新状态，再填写成功响应。
5. 响应中尽量返回处理后的实际状态。

## 状态型服务

服务端可以保存状态，例如航点列表或当前机器人模式：

```text
请求前状态
    ↓
检查请求是否合法
    ↓
合法：修改状态
非法：保持原状态
    ↓
填写响应
```

修改容器时要注意边界：

```cpp
waypoints_.erase(waypoints_.begin() + index);
```

`erase()` 接收迭代器，`waypoints_.begin() + index` 表示索引对应元素的位置。删除前必须确保索引有效。

循环访问容器时应使用：

```cpp
for (std::size_t index = 0; index < values.size(); ++index)
```

不能使用 `index <= values.size()`，否则最后一次会访问越界元素。

## C++ 构建配置

```cmake
find_package(rclcpp REQUIRED)
find_package(base_interfaces REQUIRED)

add_executable(sum_server src/sum_server.cpp)
ament_target_dependencies(sum_server rclcpp base_interfaces)

add_executable(sum_client src/sum_client.cpp)
ament_target_dependencies(sum_client rclcpp base_interfaces)

install(TARGETS
  sum_server
  sum_client
  DESTINATION lib/${PROJECT_NAME}
)
```

`package.xml` 同样需要声明 `rclcpp` 和自定义接口功能包依赖。

## 回调与执行器

普通短服务回调可以使用单线程执行器。如果服务回调执行时间很长：

- 其他定时器、订阅和服务回调可能被阻塞。
- 客户端会长时间收不到响应。
- 任务无法自然反馈进度或取消。

不要用服务模拟长时间任务。需要连续反馈和取消时，应改用动作。

## 常见问题

### 客户端一直显示服务端连接中

检查：

- 服务端是否启动。
- 服务名称是否一致。
- 服务类型是否一致。
- 是否重新 `source install/setup.bash`。
- `ROS_DOMAIN_ID` 是否一致。

### C++ 客户端段错误

常见原因：

- 非 `void` 函数遗漏 `return`。
- Future 尚未完成就访问结果。
- 请求或节点对象生命周期已经结束。
- 命令行参数数量不足却访问了 `argv`。
- `std::stof()`、`std::stod()` 转换异常未处理。

### Python `future.result()` 是 `None`

检查：

- 是否调用了 `spin_until_future_complete()`。
- Future 是否真的完成。
- 服务端回调是否返回了 `response`。
- 是否在异常路径继续访问 `response`。

### 按 `Ctrl+C` 出现重复 shutdown

在 `finally` 中先判断：

```python
if rclpy.ok():
    rclpy.shutdown()
```

这样可以避免同一个 Context 被关闭两次。
